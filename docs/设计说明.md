# 设计说明：制造工艺质量知识图谱 · GraphRAG 归因问答平台

> 数据快照：seed=42，GLM-4.5-AIR + embedding-3，320 段真实抽取；评测口径 v2（150 题：50 单跳 / 50 多跳 / 35 聚合列表 / 15 数值计数）
> 配套文档：[README.md](../README.md)（快速上手 / API 速查 / 完整评测指标）

---

## 1. 这个项目解决什么问题

制造业现场（SMT/组装/注塑车间）的质量知识分散在三类文档里：

| 体裁        | 文件   | 内容                     | 现场用途      |
| --------- | ---- | ---------------------- | --------- |
| SOP 作业指导书 | 70 份 | 工序、设备、耗用物料、重点拦截不良      | 标准作业      |
| EX 异常处理单  | 90 份 | 批次不良现象 → 根因分析 → 临时遏制措施 | 事后追责、临时止血 |
| NTC 工艺通知单 | 40 份 | 根因 → 工程永久对策 → 标准化横展    | 根治、闭环     |

真实业务痛点：**「某产品出现某不良，永久对策是什么？」** 这种问题需要跨文档推理——异常单只写根因，永久对策在通知单里，靠人翻文档平均要十几分钟。普通向量 RAG 只能检索"语义最像的一段文字"，无法保证沿着「不良 → 原因 → 对策 → 作用工序/设备」的因果链完整召回。

本项目的答案：把文档抽成**结构化知识图谱**，用 GraphRAG 沿显式关系做多跳遍历，并与 BM25、向量 RAG 做三路对比和消融评测，用 150 道带金标的题量化"图谱到底好在哪"。

## 2. 总体架构

```
                          ┌────────────────────────── 后端 FastAPI (:8010) ──────────────────────────┐
200 份 TXT 语料 ──► 节点1-2    节点3 LLM抽取      节点4 对齐        节点5 入图        节点6 索引
(SOP/EX/NTC)       本体+金标   GLM-4.5-AIR 320段  别名/纠错/embed   Neo4j/内存图库     BM25+faiss
                          │          │                  │                │                │
                          │          ▼                  ▼                ▼                ▼
                          │   entities.jsonl      entities_aligned   4672 节点         bm25.pkl
                          │   relations.jsonl     relations_aligned  8891 关系         chunks.faiss
                          └──────────────────────────────────────────────────────────────┬─────┘
                                                                                         │
                              节点7 三路检索（BM25 / 向量 / GraphRAG 因果链遍历）           │
                              节点8 四路答案（bm25/vector/graph/hybrid）+ LLM 自然语言答复   │
                              节点9 评测：300 抽检 F1 + 150 题 Hit@3/MRR/准确率 + 消融      │
                                                                                         │
        前端 React + Vite (:5173) ── 流水线编排 / G6 图谱浏览 / 三路问答对比 / ECharts 看板 ◄┘
```

**双后端设计**：图存储层是 `GraphStore` 抽象（[graphstore/base.py](../backend/app/graphstore/base.py)），Neo4j 与内存图库同构实现。Docker 里的 Neo4j 没起时自动降级内存图库（快照落盘 `data/graph/memory_graph.json`），全链路照跑，评测数字一致。

**零 Key 也能跑**：`LLM_PROVIDER=mock` 时节点 3 走分层词典+句式规则（还刻意模拟了词典不全、错别字导致的漏召），embedding 降级为 TF-IDF 哈希向量。

## 3. 领域 Schema（6 实体 / 9 关系，闭域）

定义在 [kg_types.py](../backend/app/kg_types.py)，是全项目唯一事实源，落盘 `data/schema/ontology.yaml`。

```
Device 设备 ──USED_IN──► Process 工序 ──USES_MATERIAL──► Material 物料
                              ▲
Defect 不良现象 ──OCCURS_AT──►┘
     │
     ├──CAUSED_BY──► Cause 原因 ──ADDRESSED_BY──► Countermeasure 对策
     │                                              └──TARGETS──► Device/Process/Material
     ├──INDUCED_BY_MATERIAL──► Material
     └──SUBCLASS_OF──► Defect
Process ──PRECEDES──► Process
```

**8D 框架下对策分三类**（评测设计的关键：三类对策语义相近但处置层级不同，必须分型建标）：

| ID 前缀  | 类型         | 出处          | 含义                           |
| ------ | ---------- | ----------- | ---------------------------- |
| `CM_`  | 工程永久对策（D6） | NTC「对策：」    | 换飞达、调温度曲线等根治动作——**多跳题的严格金标** |
| `CMT_` | 临时遏制措施（D3） | EX「临时遏制措施：」 | 全检、隔离、换备用设备，只止血不治根           |
| `CMS_` | 标准化横展（D7）  | NTC「标准化：」   | 更新 SOP/TPM 点检表、培训、纳 PFMEA    |

**多跳断点设计**：根因对策只出现在 NTC，而「不良→原因」只出现在 EX。约 7000+ 条因果边跨文档分布，单文档检索永远无法拼出完整链——这是 GraphRAG 优势的结构性来源，不是人为编数。

噪声注入（语料生成时）：别名口语化（虚焊/假焊、立碑/墓碑效应）、3% 错别字（锡→夕、检→捡等 9 个混淆字）、全半角/单位变体（℃/度）、12% 长实体重述（去产品前缀）。

| 6   | 双路索引      | [s6_index.py](../backend/app/pipeline/nodes/s6_index.py)       | BM25(jieba) + faiss 向量 + 实体别名表/语义链接索引                            |
| 7   | 三路检索      | [s7_retrieve.py](../backend/app/pipeline/nodes/s7_retrieve.py) | 150 题 → `retrieval_trace.jsonl` 全程留痕                             |
| 8   | 归因问答      | [s8_qa.py](../backend/app/pipeline/nodes/s8_qa.py)             | 四路结构化答案 + 证据三元组 + LLM 自然语言答复                                     |
| 9   | 评测消融      | [s9_evaluate.py](../backend/app/pipeline/nodes/s9_evaluate.py) | `metrics_summary.json` + `per_question.csv`                      |

### 4.1 节点 3 的工程设计（抽取链路核心）

- **体裁感知 prompt**：EX/NTC/SOP 各有抽取要点提示 + 两个 few-shot（异常块、通知单条目），明确要求原因/对策保留"产品：内容"完整前缀
- **分块策略**：NTC 按 `N. 适用产品` 条目、EX 按 `N. 责任工序` 不良块切分，相邻条目打包到 ≤2600 字/段（条目内关系闭环，无跨条目边，切分不破坏关系）；200 文档 → 320 段（SOP 70 / EX 90 / NTC 160）
- **段内偏移换算**：打包段是原文连续子串，mention 偏移加段首 base 即全文偏移
- **可靠性四件套**：prompt 级 SQLite 缓存、段级 checkpoint 续跑（`.extract_chunks.jsonl`）、429/5xx/超时指数退避（2/5/10/20/30s）、JSON 截断正则抢救（部分召回不丢整篇）
- **版本失效**：模式键 `provider:model:PROMPT_VERSION`，改 prompt 必须升版本号，旧产物自动全量重跑

### 4.2 节点 4 对齐的四通道

1. **别名表精确归一**：种子库全量别名（抽取词典的超集）
2. **后缀归一**：去产品前缀的复述（"预热不充分，助焊剂活化不足" → "U7超声波水表板：预热不充分…"，唯一后缀才合并）
3. **一字符纠错**：9 个已知混淆字反向替换 + 短名编辑距离 1
4. **embedding 聚类**：同标签最近邻，全局阈值 0.82；原因/对策走**产品级匹配**（0.68/0.60 阈值 + top1 唯一），防止"H6 的预热不足"错并到"U7 的预热不足"

### 4.3 GraphRAG 检索逻辑（[retrieval/engine.py](../backend/app/retrieval/engine.py)）

- **实体链接**：别名表最长匹配优先 → embedding 语义补链（阈值 0.45）
- **带产品约束的定向 2 跳**（`_scoped_causal`）：问题含产品时，`Defect →(本产品) Cause →(本产品) CM`，产品代码过滤防止跨产品串答案
- **无产品约束**：走图库 `causal_paths`，分别取 1 跳（工序/物料/原因）和 2 跳（原因→对策），避免变长路径混合后截断
- **工序/物料入口**：反向 OCCURS_AT/INDUCED_BY_MATERIAL 找缺陷，再正向展开因果链

## 5. 评测体系（这是项目最值钱的部分）

### 5.1 金标从哪来

不是人工标注，而是**生成即金标**：节点 2 用种子库渲染文档时，每个实体写入都记录字符偏移，每条关系同步落盘（`corpus_gold.jsonl`），seed=42 逐字节可复现。语料库总量：**4,906 个被提及实体 / 9,491 条唯一关系**（KB 实体池 6,036，场景 576 个，覆盖原因/对策各 1,401 个）。

### 5.2 三套指标

| 层   | 样本                                  | 指标                   | 口径                             |
| --- | ----------------------------------- | -------------------- | ------------------------------ |
| 抽取  | 300 条抽检（150 mention + 150 三元组，随机冻结） | P/R/F1               | 实体=文档级规范 ID 集合；关系=语料级唯一三元组集合   |
| 检索  | 150 题（50 单跳 / 50 多跳 / 35 聚合列表 / 15 数值计数） | Hit@3、MRR、coverage@3/10 | 三路分别算，同预算同过滤                 |
| 端到端 | 同上                                  | 准确率                  | 列表题：覆盖率≥70% 且精确率≥50%；数值题 ±1 容差 |

### 5.3 实测结果（公平口径 v2，GLM-4.5-AIR + embedding-3，内存图库）

**抽取层**

|     | P    | R    | F1       |
| --- | ---- | ---- | -------- |
| 实体  | 0.92 | 0.91 | **0.92** |
| 关系  | 0.84 | 0.79 | **0.81** |

**Hit@3（BM25 / 向量 / GraphRAG）**：单跳 0.70/0.82/**0.88**；多跳 0.58/0.88/**0.98**；聚合列表 0.83/0.74/**0.91**；多跳 MRR 0.49/0.77/**0.87**

**多答案覆盖率 coverage@3 / @10（多跳题）**：BM25 0.24/0.47、向量 0.42/0.62、**GraphRAG 0.76/0.81**

**端到端准确率**：多跳 BM25 0.04、向量 0.04、**GraphRAG 0.68**（数值计数题 GraphRAG 1.00）；消融关图谱后多跳准确率 0.68 → **0.04**

完整数字以 [metrics_summary.json](../backend/data/eval/metrics_summary.json) 为准。

## 7. 关键设计取舍

1. **为什么不用纯向量 RAG**：答案完整性无法保证。多跳题金标是一个产品某缺陷的全部根因对策，向量 top-k chunk 召回率天然受限（多跳 coverage@3 仅 0.42、coverage@10 0.62）；图谱沿 CAUSED_BY+ADDRESSED_BY 遍历是"闭世界枚举"，coverage@3 0.76、@10 0.81——这是端到端准确率 0.68 vs 0.04 差距的直接来源。
2. **为什么还用向量做融合**：图谱依赖实体链接成功，开放表述/别名未登录时链接会断；向量做语义兜底，双路融合（图优先、向量补同类型实体）是默认架构。
3. **LLM vs 规则抽取的实测对照**：mock 规则在合成语料上实体 F1 0.90，真实 LLM 0.92 略优、关系 F1 反而略低（0.81 vs 0.85，长 TARGETS 边漏连）。结论：高规范闭域结构用规则性价比极高，开放长尾、跨句式表述才是 LLM 的增量。
4. **为什么评测要分单跳/多跳/聚合/数值**：公平口径下三路检索 Hit@3 差距在单跳上明显收窄（0.88 vs 0.82），多跳检索仍有 0.98 vs 0.88 的差距，但真正的质变出现在端到端（多跳 0.68 vs 0.04）与数值结构计数题（1.00 vs 0–0.40）——不分层、不拆数值题会得出"图谱没啥用"的错误结论。
5. **产品上下文保护**：同一根因文本在不同产品下是不同实体（不同的参数、责任工序），对齐和检索两侧都必须带产品代码过滤，否则跨产品串答案。
